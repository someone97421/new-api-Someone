# 上游对齐与媒体能力插件化重构执行计划

## 目标与已确认决策

以官方上游为主干能力来源，将本项目维护范围收缩为供应商插件和必要的媒体宿主扩展。官方已有明确替代方案的功能使用官方实现；原有定制中明确未被覆盖的能力继续保留，不因重构改变实际接口效果。

已确认：

- 保留 Gemini 原生生图到 OpenAI Images 的适配。
- 保留同步生图转后台异步作业的能力。
- 保留媒体结果本地保存、保留期限和过期清理。
- 原有定制中的其他明确缺口按本计划的功能清单处理；不扩展为实现任意上游缺失的新功能。
- 能插件化的供应商逻辑优先插件化，减少修改 Go 核心与前端通用表单。
- 目前没有用户，不实现旧数据兼容层、历史配置迁移、旧渠道编号迁移或历史任务恢复。
- 不恢复整套旧分支。以当前分支和最新官方架构为基础，按需求提取实现。
- 本文作为单个 agent 一次性长程执行的任务书。执行者接到实施指令后连续推进到交付，阶段是内部检查点，不是逐阶段等待用户批准的停靠点。

不需要兼容或迁移不等于授权删除现有数据库、文件、分支或部署资源。开发采用新配置和新建数据进行验收，不在重构过程中自动清理现有环境。

| 同步请求转后台异步作业 | 宿主媒体执行能力 | 保留显式异步入口与后台完成语义，优先复用官方任务基础设施 |
| 原生异步任务轮询、提交重试、结算 | 官方任务宿主 | 不另建同用途的供应商轮询和扣费系统 |
| 混合同步/异步供应商的生图主备 | 官方选渠重试＋媒体执行扩展 | 保留提交失败换渠，任务受理后固定原渠道 |
| 本地媒体归档、下载、到期清理 | 宿主存储模块 | 插件只描述产物，宿主负责下载、保存和清理 |
| 管理员任务原始数据查看 | 小型管理扩展 | 保留按需加载入口；不把整个数据体塞进任务列表 |
| 原任务请求/响应诊断信息 | 小型管理扩展 | 保留有用诊断，隐藏凭据与二进制正文，区分实际存储快照和完整 HTTP 抓包 |
| 任务详情内的计费展示 | 官方组件，必要时补入口 | 复用同一计费数据与展示组件，不维护第二套计算规则 |
| `TaskEnabled` 管理开关 | 官方选项的小型 UI 扩展 | 若实施基线仍缺入口则保留；复用官方后端选项 |

“插件化可实现”不等于已有现成官方适配。自定义插件交付前，不能宣布对应旧能力已经被替代。

## 目标结构

### 供应商插件

以单文件 JS 任务插件承载供应商协议差异，包括请求构建、字段转换、任务状态解析、用量事实、结果展示与产物描述。使用官方上传、启用、版本管理和渠道绑定机制。

第一批范围：

1. Gemini 原生图片生成与 OpenAI Images 之间的适配。
2. 实际需要的非标准 OpenAI 兼容图片任务适配。
3. 实际需要的非标准 OpenAI 兼容视频任务适配。

插件按稳定协议边界拆分，不为仅 Base URL 或密钥不同的站点重复复制插件，也不为假设中的供应商创建适配器。可配置能力优先使用官方现有上下文和设置；不假设宿主已经支持任意插件私有配置。

每个插件须有明确的模型、请求字段、响应结构、任务状态、计费事实和内容获取契约。保留官方要求的项目标识与版权归属。

### 媒体执行扩展

负责将显式选择异步执行的请求转成可查询作业，使客户端断开不终止已经受理的工作。

优先复用官方任务持久化、调度、查询、产物、计费和退款能力。只有官方任务契约无法承接同步 Relay 后台执行时，才添加最小执行记录或调度扩展，并明确它与官方 Task 的关系。

不默认恢复旧 `async_media_jobs` / `async_media_files` 全套表结构，也不先设计一套通用队列平台。实现阶段先证明最小链路，再决定必要数据结构。

同步客户端继续获得标准同步 Images 响应。显式异步客户端获得受理响应、作业标识及查询入口；异步包装不得意外接管普通请求。具体路由须先检查官方端点所有权，避免占用 `/v1/tasks` 等已存在的通用接口。

### 媒体存储扩展

负责产物归档、本地文件读取、保留期限和过期清理；接入任务产物读取链路，避免维护两份互相矛盾的任务结果。

官方 JS 插件没有文件系统和后台执行能力，不能把落盘、清理或长时间轮询写进插件。宿主只暴露完成业务所需的最小能力，不扩大插件沙箱权限。

第一版使用本地存储，支持配置目录与保留期限。不扩展对象存储、多区域复制或通用存储框架。

## 必须明确的行为契约

### Gemini Images

- `/v1/images/generations` 返回客户端预期的 Images JSON，不以聊天 Markdown 图片字符串代替。
- 参考图、比例、尺寸、质量、输出格式等字段逐项映射；哪些支持、哪些拒绝、哪些通过供应商扩展传递须在插件说明中明确。
- `imageConfig` 与兼容站使用的其他结构按实际供应商协议区分；实施前核对当前可靠文档或已有真实响应，不能仅依据旧提交名称认定官方格式。
- 显式 `0`、`false` 与字段未填写保持区别；数量和其他计费乘数沿用宿主边界校验。
- 图片多产物、Base64 与 URL 响应、模型别名和请求失败均有确定行为。

### 异步执行与故障转移

- 作业被受理后，即使客户端断开，也能通过作业标识查询结果。
- 未成功提交上游时使用官方渠道重试策略；上游返回任务 ID 后固定渠道，不因查询错误另选渠道重新生成。
- 重启后的待执行、执行中与已提交任务分别有明确处理规则。同步上游在“请求已发出但结果未记录”窗口不能被静默重复提交。
- 临时轮询错误、上游终态失败、观察超时和本地产物归档失败必须区分。
- 扣费、退款和完成结算只有一条权威链路；作业包装和文件保存不产生第二次生成费用。

### 本地存储

- 明确保留对象是生成产物；输入暂存和诊断快照只有在执行或排障确有需要时保留。
- 归档成功后，下载不再依赖供应商临时 URL 的有效期。
- 任务完成与归档状态分别记录；归档失败不能伪造生成失败或自动触发重新生成。
- 明确保留期限起算点、过期后的接口响应及清理重试行为。
- 复用现有身份与访问控制，凭据不进入产物、日志或公开下载响应。

## 验收与执行约束

本计划列出后续验收要求，不表示已执行任何测试，也不改变项目“默认不主动运行测试、验证或构建”的约定。实施时在用户授权范围内安排与修改直接相关的最小检查，全量检查须明确授权。

重点验收：

| 场景 | 应观察到的结果 |
| --- | --- |
| Gemini 文生图、参考图生成 | 正确 Images 响应与参数映射 |
| 自定义图片/视频端点 | 正确提交、查询、状态映射和内容读取 |
| 同步调用与显式异步调用 | 各自保持约定的响应方式 |
| 客户端在受理后断开 | 作业继续，能够查询终态 |
| 提交失败与查询失败 | 仅在允许阶段重试或换渠 |
| 重启与重复调度 | 无静默重复生成、重复扣费或退款 |
| 实际用量与预估不同 | 官方结算链路正确处理差额 |
| 本地归档与上游链接失效 | 已保存产物仍可访问 |
| 到期清理与归档失败 | 状态、接口与文件生命周期一致 |
| 管理员诊断 | 按权限读取必要数据，不暴露凭据 |

涉及数据库行为的实现必须按仓库规定在真实 SQLite、MySQL、PostgreSQL 上完成相应验证；无法执行时记录阻塞，不宣称数据库兼容或该阶段已完整验收。对官方数据模型和已有数据的保全要求与本项目“不为旧定制数据提供迁移”是两件事，应按实际改动范围区分。

修改 `relaykit/` 或其公开接口时必须满足独立构建要求：`cd relaykit && GOWORK=off go build ./...`。没有相关授权或环境时明确列为待完成项，不以根模块构建代替。

后台服务仅在可见终端中前台运行，终端关闭时一并退出。不得为开发验证静默启动服务。新增回归用例围绕接口、计费和持久化行为，优先扩展已有合适文件，不按代码层重复铺设测试。

## 长程执行规则

执行目标是完成本计划全部范围的代码、插件、配置说明与获准验收。默认由一个 agent 持续执行；不因某个阶段完成、一次上下文压缩或发现普通实现问题而结束任务等待“继续”。

### 工作顺序与成本控制

1. 读取本计划、适用的仓库约定和现有进度记录，确认工作区已有修改。
2. 仅补齐阶段 0 的具体未知项，形成足够实施的决定后立即进入代码工作；不重复整仓比较或无限完善设计。
3. 按依赖顺序连续完成阶段 1 至 5。先打通一个可用的端到端链路，再补齐同一范围的字段、失败分支和管理入口。
4. 普通命名、文件位置、内部接口、插件拆分和局部重构由执行者自行决定，简要记录理由即可。不要把这些实现细节变成用户问卷。
5. 优先直接执行；只有独立调查或并行实现确实节省成本时才委派。避免反复派审查代理、重复读取已确认文件或重复运行已通过的检查。
6. 每次额外调查、修改和检查都对应一个未完成需求、明确缺陷或具体不确定性。达到完成标准后收尾，不扩展外围架构和无关优化。

### 阻塞处理

- 缺少供应商密钥或真实测试环境时，先完成能依据协议、源码和已有样例实现的部分，记录待实测事项，继续其他独立工作；不编造已验证结论。
- 插件 API 无法承载某一步时，定位具体缺少的宿主能力，按已授权的最小宿主扩展方向处理，不能因此把整个功能留成 TODO。
- 某一路径反复失败时，汇总证据并换一个更窄的解决步骤；不要无限重试同一搜索、编辑或构建。
- 必須由用户决定的范围变化、凭据缺失或受约束操作集中说明；只暂停依赖该决定的部分，继续其余工作。遵守明确的用户停止指令。
- 测试授权与项目强制检查遵循前一节。受阻的验收单独列出，不妨碍完成其余已授权实现，也不能被标记为通过。
